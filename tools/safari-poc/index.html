Safari /play POC

Reproduces, without Qt, the browser behaviour behind the /play fixes. Each "Qt window" below is the same DOM shape Qt wasm builds: a shadow root holding a window div, a canvas, a contenteditable focus helper and a hidden IME input. "Late" means handled from a queue after dispatch finished, which is what Qt's JSPI suspend/resume control does when the instance is suspended outside processEvents(). "Microtask" is its resume path.




A. Event target after dispatch (desktop crash)


Move the mouse into and out of the grey box, then click or right-click it. Claim: read late, composedPath() is empty for every event; target becomes the shadow host for composed events (click) but null for non-composed ones (pointerenter/pointerleave), which is the desktop crash. Pinning them at dispatch keeps them.







B. Focus and keys (right-click / dead keys / macOS accent popup)


1. Press Focus helper (what Qt's focus() does). 2. Type: the counter is "keys reaching Qt". 3. Click or right-click the grey box with each pointerdown mode, then type again. 4. Hold a with each keydown mode to see the press-and-hold accent popup.



  
  
  










C. Mobile keyboard (tap a text field)


On a phone: tap the grey box ("a Qt text field"). Qt focuses its hidden input in the pointer handler and cancels the pointerdown default. Try each combination and watch whether the keyboard stays, closes again, or never opens; the log shows input focus/blur.



  
  
  








D. OPFS from a Worker vs the main thread


Claims: (1) a Worker's async OPFS calls (lookups, getFile()) only settle in Safari while the page's main thread is free, so they stall while it is blocked; (2) SyncAccessHandle reads in a Worker do not need the main thread; (3) every async OPFS call made from the main thread is an await, i.e. a JSPI suspension in /play, and with it a window in which Qt queues events. Needs a secure context (https or localhost).
